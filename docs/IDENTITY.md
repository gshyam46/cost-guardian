# Named identity for an isolated project (R2-01)

Recorded 2026-09-11 before implementation. This extends [ACCESS.md](ACCESS.md) with an opt-in OIDC mode. Existing `api_key` mode remains a local development compatibility path. OIDC mode never accepts that shared key as a fallback. The first deployment boundary is one organization/project/environment and one telemetry connection per Guardian database; there is no project selector or shared-tenant hosting claim.

## Configuration and authority

The 2026-09-12 extension in [CAPTURE.md](CAPTURE.md) adds owner-managed write-only ingestion keys for direct capture. It retains these read/resolve permission arrays, independently enforces owner plus CSRF for key mutations, and uses the same fixed identity binding. Keys are project credentials: creator logout/removal does not revoke them. Explicitly rotate/revoke ingestion keys in Setup. The native numeric path is locally implemented; provider deployment, account administration and real no-telemetry activation remain separate gates.

`GUARDIAN_AUTH_MODE` is `api_key` (default) or `oidc`; any other value fails closed. OIDC requires `GUARDIAN_OIDC_ISSUER`, `GUARDIAN_OIDC_CLIENT_ID`, `GUARDIAN_OIDC_CLIENT_SECRET`, `GUARDIAN_PUBLIC_URL`, `GUARDIAN_ORGANIZATION_ID`, `GUARDIAN_PROJECT_ID`, `GUARDIAN_ENVIRONMENT`, `GUARDIAN_PROJECT_NAME` and `GUARDIAN_OIDC_MEMBERS_JSON`. Membership is an operator-managed JSON list of `{subject, role, name}` with unique issuer subjects and roles `owner`, `operator`, `viewer`. Names are operator display labels; identity is the verified issuer plus subject, never an email address or browser role claim. At least one owner is required. Role/config changes require consistent configuration and process restart across replicas; membership administration UI is later work.

Production public URL is an HTTPS origin serving frontend and API through the same origin. Callback is the fixed `/api/guardian/auth/callback`. Optional `GUARDIAN_UI_ORIGIN` defaults to the public origin; a different origin is allowed only for explicit loopback development with `GUARDIAN_ALLOW_INSECURE_LOCAL_AUTH=true`. This exception permits HTTP loopback identity/UI/API URLs and nonsecure development cookies; it is not a hosted deployment configuration. CORS is explicit in OIDC mode and cookie mutations require the exact configured UI Origin. Public/UI origins canonicalize host casing, default ports and IPv6 spelling before comparison; issuer strings remain exact. Configure international public hostnames using their ASCII punycode form.

Pin organization/project/environment/connection/issuer/client ID as an atomic database binding before accepting sessions. A mismatched binding or existing ledger connection refuses access; never reinterpret old data as another project's data. Reads continue through the isolated database/source/cache configured for that deployment. This binding prevents accidental reassignment; it does not certify ownership of an upstream vendor project or implement multi-project storage isolation.

## Protocol and API

- `GET /api/guardian/auth/config`: noncacheable public `{auth_mode: "api_key"|"oidc", login_path: null|"/api/guardian/auth/login"}`. Invalid configuration returns safe 503. It verifies configuration shape, not provider readiness. It returns no client secret or issuer credentials.
- `GET /api/guardian/auth/login`: OIDC code flow with S256 PKCE, nonce and one-use state bound to a separate HttpOnly browser cookie. Login state expires after ten minutes and is atomically consumed before code exchange. State/cookie mismatch, replay or expiry cannot contact the token endpoint. Login admission is bounded; repeated attempts may receive 429/503 and retry guidance.
- `GET /api/guardian/auth/callback`: verify signed RS256 ID token, issuer, audience/authorized party, subject, expiry, issuance time and nonce. Authlib and its maintained JOSE implementation perform the protocol/cryptographic work. Discard provider access/ID/refresh tokens after verification. Issue a fresh opaque application session; invalidate a prior session presented by the same browser. Redirect only to configured UI origin with `/?guardian_login=complete` or the fixed safe failure marker `/?guardian_login=failed`. No caller-controlled return URL is accepted by the server.
- `GET /api/guardian/access`: legacy mode retains its exact existing response. OIDC response is `{authenticated:true, auth_mode:"oidc", deployment_mode:"single_project", permissions:[...], actor:{id,name,role}, project:{organization_id,project_id,environment,name}, csrf_token:"..."}`. Permissions are `["read"]` for viewer and `["read","resolve_incidents"]` for owner/operator. This verifies an unexpired database session, current operator membership and deployment binding. It does not imply active telemetry or provisioning.
- `POST /api/guardian/auth/logout`: require valid session, exact UI `Origin` and `X-Guardian-CSRF` matching that session; revoke it server-side, clear the cookie, return 204. Failure cannot be described as confirmed server logout. This is local application logout, not identity-provider-wide logout.
- Existing authenticated data routes use the configured mode. OIDC incident resolution additionally requires operator/owner and CSRF/Origin. Viewer mutation returns 403 before incident reads. Within one Mongo transaction, recheck/touch session and binding, transition open to resolved, and insert a deterministic actor/project/action audit event. Repeated resolution preserves the original resolution time and creates no extra audit event. Session touch conflicts with concurrent logout so a revoked session cannot later commit an authorized transition.

Session lifetime is eight hours absolute. Use random opaque identifiers, hash them at rest, explicitly check expiry on each request, and use Mongo TTL only for cleanup. Production cookies use the `__Host-` prefix, Path `/`, Secure, HttpOnly and SameSite=Lax; local-development cookie names omit the prefix when Secure is disabled. Browser JavaScript receives neither session identifiers nor provider tokens. The CSRF token is session-bound and retained only in memory by the UI. A database outage returns unavailable access, not a verified or anonymous fallback.

## Browser behavior

Load auth configuration before consulting saved legacy keys. In OIDC mode never read/send a saved shared key. Use cookie credentials against the configured Guardian API; require same-origin production deployment. Store only a validated local deep-link pathname for the login round trip, with no external/protocol-relative/backslash/control-character targets. On callback success restore that route after session verification; on failure show retry without a redirect loop.

Keep actor/project/permissions/CSRF in memory. Viewer UI hides resolution controls; the API independently enforces permissions. A current-session 401 unmounts protected content; a stale response cannot remove a replacement session. For logout, unmount protected views immediately, report server failure with retry, and broadcast only a nonsecret logout notification after confirmed logout. Reload or cross-tab changes revalidate the server session. Legacy access recovery remains covered by its existing tests.

## Storage, operations and evidence

New collections hold short-lived login transactions, hashed application sessions, login admission counters and redacted identity audit events. An identity binding lives in `guardian_state`. No automatic legacy data migration or deletion is performed. Session and flow operations have bounded application/server waits; identity-provider requests have bounded bodies/timeouts and do not follow redirects or inherit proxy credentials. Redact callback query strings from application/HTTP access logs; provider error descriptions, authorization codes, state values and tokens are excluded from reports/audits.

Acceptance includes real signed-token fixtures over controlled provider HTTP transport, one-use browser-bound state, invalid-token/nonce/audience cases, key-fallback denial, exact Origin/CSRF, role denial before target reads, expiry/logout, binding mismatch, transactional resolve/audit rollback and concurrent replay. Use actual local Mongo for session consumption/resolve atomicity; mocks alone do not establish it. Browser scenarios cover legacy mode plus OIDC entry, viewer/operator, expiry/logout failure and safe return paths. Record actual checks and remaining limits in [VALIDATION.md](VALIDATION.md).

This implements the named-access foundation for an isolated project. Actual identity-provider registration/deployed TLS callback tests, member invitations/removal/session administration, provisioning and real no-telemetry activation remain release gates. Scoped direct-mode ingestion credentials are now implemented under [CAPTURE.md](CAPTURE.md). Local synthetic authentication does not close those gates.

## Operator setup and rollout

For the packaged direct-capture path, use the [deployment operator guide](../deploy/guardian/README.md). Its explicit bootstrap pins the compatible identity/source binding and initializes indexes before the first login; the manual setup below retains first-flow initialization for existing development entrypoints. Packaged commands disable dotenv and accept bounded secret files. Native local sign-in evidence does not replace verification against the actual provider and public TLS origin.

The implementation is opt-in; existing development environments continue in `api_key` mode. Install backend requirements with the constraints file. Authlib 1.8.0 uses its own HTTPX2 transport; the existing telemetry HTTPX 0.28.1 adapter is unchanged. Dependency pins and local tests do not constitute a vulnerability audit or deployed-provider compatibility result.

1. Select a dedicated Guardian database on a transaction-capable Mongo replica set. The database identity must match its existing ledger connection. Give the application access to its identity collections and TTL-index creation; every flow/session/admission write uses majority acknowledgement with a three-second acknowledgement limit. Authorization reads use majority concern; action/session-rotation transactions use snapshot reads and majority commits. Local single-node tests do not establish multi-node failover behavior.
2. Register a confidential OIDC client with an operator-trusted issuer. Require authorization-code flow, `client_secret_basic`, PKCE S256, query response mode and RS256 ID tokens; request `openid profile`. Register exactly `https://your-guardian-host/api/guardian/auth/callback`. Discovery must identify the exact issuer and supply HTTPS, credential-free, query-free authorization/token/JWKS endpoints. Redirecting metadata/token endpoints are unsupported. No user-info call, provider-token refresh or provider-wide logout is implemented.
3. Set all OIDC values from the backend environment example using the deployment's secret configuration. Use stable organization/project/environment/connection identifiers and exact issuer subject IDs in `GUARDIAN_OIDC_MEMBERS_JSON`; subject IDs are ASCII and at most 255 characters. Use a JSON list such as `[{"subject":"verified-owner-subject","role":"owner","name":"Team owner"},{"subject":"verified-viewer-subject","role":"viewer","name":"Support viewer"}]`. Do not grant authority by email, domain or provider display name. There are at most 100 configured members and at least one owner.
4. Build the frontend with `REACT_APP_GUARDIAN_URL=/`, unset, or equal to the public HTTPS origin. Production builds default to the current browser origin; a copied development `.env` may still override that setting. Serve the SPA and `/api` through the same origin, preserve the API prefix, and route SPA deep links to `index.html` without sending API requests there. Forward `Origin`, cookies and `X-Guardian-CSRF`; configure the proxy to log callback paths without query strings. Guardian redacts its own Uvicorn and HTTP-client callback logs, including slash redirects and encoded paths; it cannot configure upstream proxy/identity-provider logging.
5. Set `GUARDIAN_AUTH_MODE=oidc`, restart replicas with consistent configuration and verify `/api/guardian/auth/config`, sign-in as an owner and viewer, protected reads, operator resolution and logout on the deployed TLS URL. The first flow pins the database binding. A binding mismatch returns unavailable; investigate configuration and restore the intended values, never delete/rewrite the binding to bypass the check. Changing the issuer/client/project boundary requires an explicit migration/new isolated deployment, not a key rotation.

For local integration development only, set `GUARDIAN_ALLOW_INSECURE_LOCAL_AUTH=true`, use loopback issuer/API/UI URLs, set `GUARDIAN_PUBLIC_URL=http://localhost:8001` and `GUARDIAN_UI_ORIGIN=http://localhost:3001`, and build/run the frontend with `REACT_APP_GUARDIAN_URL=http://localhost:8001`. Keep the same loopback hostname for UI and API so SameSite cookies work. The local provider must register the exact HTTP callback. The exception refuses public hosts; never enable it for hosted customers.

The API allows 20 sign-in attempts per ASGI client address and 200 across the deployment in each five-minute window. Counter expiry is cleanup only. The ASGI server may resolve client addresses through its trusted-proxy configuration; configure that trust explicitly and never trust arbitrary forwarding headers. Guardian does not parse those headers again. A shared proxy can cause peers to share the lower limit; capacity and admission design remain operating work. Provider operations admit four concurrent requests per process, wait at most 250ms for a slot, and have a 15-second adapter deadline. Mongo read/state operations have a five-second application deadline; transactional rotation/resolution allows 35 seconds including commit retry. A timed-out mutation may have committed: refresh the incident and retry the same resolution safely; its time/audit identity are stable.

Only identity-binding, short-lived flow/session/admission and redacted action-audit records are added. Existing incident data is unchanged until an authorized user resolves it. Session/flow IDs are SHA-256 hashed at rest. TTL removes expired ephemeral records eventually; audit events are retained until an explicit retention/offboarding procedure is supplied. Audit records contain actor ID/name/role, project labels, action/time and incident ID, without raw incident evidence, provider tokens or session/CSRF values. Member/session administration, audit browsing/export and deletion/retention controls remain planned.

Removing a member or changing a role in consistent operator configuration affects subsequent authorization after process restart; there is no self-service member removal or cross-replica configuration distributor. Emergency revocation and replacement-session administration still need an operator tool. Rolling back the application requires preserving the database and supported identity mode; do not expose the shared-key development mode as a hosted rollback. Secure deployment, XSS/CSP hardening, secret closure and end-to-end provider/TLS checks remain launch gates.
