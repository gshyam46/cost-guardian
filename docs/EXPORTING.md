# Background export and call lifecycle (R2-02)

Contract recorded 2026-09-12 before code; bounded implementation and local integration checks are complete, with results in [VALIDATION.md](VALIDATION.md). This extends the manual [capture contract](CAPTURE.md) with dependency-free Python and Node background exporters and provider-neutral call handles. It removes the requirement to implement a queue for the supported long-running server process. It does not implement durable disk delivery, automatic provider instrumentation, serverless shutdown guarantees, OTLP or the RAG retrieval/embedding/workflow schema. API event version 1 and existing numeric ledger behavior stay unchanged.

## Customer contract

For supported OpenAI calls, use [PROVIDERS.md](PROVIDERS.md) and the [copyable recipes](../examples/native-capture/README.md). The new `guardian_openai` helpers extract validated final usage while preserving provider behavior. The provider-neutral `python_app`/`node_app` helpers described below still leave measurements unknown unless the caller supplies them; their generic EOF status rule is not the provider adapter's semantic-completion contract. Both use the same exporter and neither calculates USD prices.

Create one exporter per application process during startup, using the existing HTTPS Guardian origin and scoped ingestion key. Importing the modules never reads configuration, starts a thread/timer or contacts a network. Construction validates local configuration and starts at most one sender worker; it cannot contact Guardian until an event is admitted. Invalid constructor options raise a fixed configuration error during explicit setup. Runtime instrumentation and admission failures return safe diagnostics rather than changing provider results or exceptions.

Python exposes `BackgroundExporter(...).emit(event)`, `start_call(agent_name=..., model=..., trace_id=None, parent_observation_id=None)`, `snapshot()`, `flush(timeout=5)` and `close(timeout=5)`. Node exposes `BackgroundExporter`, synchronous `emit(event)` and `startCall({...})`, `snapshot()`, and Promise-returning `flush(timeoutMs=5000)` / `close(timeoutMs=5000)`. Emit is local validation/copy/admission only; it performs no network call or transport wait. Node schedules I/O on a later turn; Python sends from one daemon worker. Reuse a process-scoped instance rather than creating one per model call.

Admission returns `{accepted:boolean, code}`. Codes are fixed: `queued`, `invalid_event`, `queue_full`, `closed`, `exporter_unavailable`. Unknown/content fields are rejected before copying or retaining an event. Accept the same flat technical identifiers, strict numeric/decimal/time fields and bounds as Guardian JSON version 1. Validate original timestamps before reducing precision; never serialize arbitrary SDK objects, result bodies, exceptions, custom JSON hooks or field values into diagnostics. Strings in identifier fields remain the application's responsibility: do not put personal/customer information in them.

One instance has an immutable `test_mode` / `testMode` boolean, default false. Test examples require explicit invocation and construct test-mode exporters. Test events and real events cannot share a batch. Local export counters describe submitted events, including caller duplicates; Guardian remains authoritative for unique accounting and analysis.

For parity across languages, exporter timestamps use `YYYY-MM-DDTHH:MM:SS[.ffffff]` with 1-6 optional fractional digits and an explicit `Z` or `+/-HH:MM` offset. Validate calendar dates and original microsecond ordering, not JavaScript's millisecond-rounded date alone. This is a deliberate subset of the backend parser's accepted ISO representations. Preserve the admitted strings through retries.

## Bounds and batching

Defaults: at most 1,000 accepted pending events and 4 MiB of serialized event bytes, including in-flight/retry work. Exceeding either bound rejects the newest event and increments the rejected counter; existing work is preserved. Constructor options may lower these bounds but cannot exceed them. Every batch contains at most 100 events and at most 256 KiB including the envelope. Keep one active batch and FIFO order. Normal batching waits up to one second from the first pending event; flush can wake unsent work sooner.

Snapshot primitive fields at admission. Mutating the caller's dictionary/object afterward cannot change queued or retried bytes. Allocate a batch UUID when forming a batch and retain the exact normalized events, ordering, timestamps and UUID for every attempt. Never rebuild an attempted batch after an uncertain acknowledgement; a changed body under an old UUID is a conflict. No callback exposed by the exporter receives credentials or raw rejected data.

Expire unsent queue entries individually before forming a batch. Preserve FIFO order: send a fresh prefix before an expired entry, then settle the expired head and continue. An expired event that has never been attempted must not cause unrelated fresh neighbors to be abandoned. After an attempt, the entire immutable batch shares its retry/expiry disposition.

## Retry and termination

The exporter owns retries through a single-attempt form of the existing native transport. Preserve the original senders' public default of at most three attempts for existing manual callers. Do not multiply nested retry loops. Each batch has at most five transport attempts and a five-minute monotonic retry/start budget from first batch construction. An already running Python urllib/DNS operation can outlast this budget; it is not a hard total transport deadline. Retry transport/unconfirmed receipts and transient HTTP errors; stop retrying permanent rejection or invalid configuration. Use exponential waits of 1, 2, 4, 8 seconds, with server Retry-After as a minimum. Flush/close may not accelerate a retry deadline. If the next attempt falls beyond the age budget, abandon the batch as unconfirmed.

Do not start an attempt if any event's original start time is outside the server's 24-hour acceptance window, if local lifetime has expired, or after close has force-stopped the exporter. Do not refresh timestamps/IDs to bypass expiry. An unconfirmed event may already be stored at Guardian; this counter means no verified receipt was obtained, not proven loss. Authentication/bad-batch rejection remains visible through fixed safe diagnostics without echoing server content.

A confirmed HTTP 401/403 sets `last_error_code=credential_rejected`, abandons pending work as unconfirmed and stops further sends/admission on that instance. Recreate the exporter with a replacement key after fixing configuration. Permanent bad-batch responses terminate that batch without endlessly retrying it. The internal single-attempt transport may return a safe numeric HTTP status for this decision; preserve the original manual sender's response shape unless an explicit internal option was selected.

Flush snapshots the last admitted sequence and waits only for that prefix, so new events cannot starve it. It returns `{drained:boolean, confirmed:boolean, stats:<snapshot>}`. `drained` means the prefix has reached a terminal disposition; `confirmed` additionally requires that every event in that prefix obtained a validated receipt. A timeout leaves pending work intact and reports false. Stats are a current global snapshot, so concurrent later events may still be pending even after the requested prefix drains.

Close immediately stops admission, then waits up to its deadline for the same prefix. On timeout it marks remaining accepted work unconfirmed and fences late completions from altering counters or starting retries. It is idempotent. A forced close must return `confirmed:false`; it may report `drained:true` once all work has a terminal unconfirmed disposition. Node aborts the in-flight request and retry timer. Python cannot interrupt an already running urllib/DNS operation safely: use a daemon thread, signal cancellation before any new attempt and report `transport_active` until that call actually returns. Close's wait stays bounded; it must not claim that such transport was stopped or that no remote commit happened. Forked Python processes must create their own exporter; inherited instances refuse admission and never restart the parent's worker.

## Diagnostics

`snapshot()` returns only fixed counters/status: `enqueued_events`, `confirmed_events`, `unconfirmed_events`, `rejected_events`, `pending_events`, `queued_events`, `in_flight_events`, `pending_bytes`, `export_attempts`, `closed`, `transport_active`, and `last_error_code` (fixed code or null). Keep counts nonnegative and reconcile `enqueued_events = confirmed_events + unconfirmed_events + pending_events`. Accepted work remains inside both capacity bounds while in flight/backing off. Invalid/full/closed admissions increment only rejected events. No event IDs, labels, URL, key, provider data or exception messages appear in snapshots. Do not log automatically or send these counters as fabricated production calls. The application can expose them through its own operational metrics.

## Call handles and streaming

`start_call` / `startCall` allocates a stable observation ID, optional generated trace ID and observed UTC start time; it stores only validated technical identity fields. The handle exposes its IDs for intentional parent/trace linkage. `finish(status, ...measurements)` / `finish({status, ...measurements})` captures the end time and locally emits one terminal event. Measurements are only `cost_usd`, `input_tokens`, `output_tokens`, `total_tokens`; unknown values remain null/omitted and no price is inferred. The first finish seals the handle even if admission fails; later finishes return `already_finished` without adding a second event. Invalid start metadata returns an inert handle and records one rejected event rather than raising inside the customer call.

Provider calls/results/errors are never inspected by the library. Application recipes explicitly finish success only after a non-streaming result or complete stream exhaustion. Exceptions finish error and then propagate the original exception unchanged. Cancellation, an early stream break or missing completion evidence finishes unknown in a finally block. A final idempotent finish cannot overwrite the first terminal result. SDK-internal retries remain opaque; explicitly observed application retries get distinct handles/observation IDs under the same trace. No workflow success or answer quality is inferred from a successful call.

Runnable Python and Node examples must exercise normal completion, stream exhaustion, early exit and failure using local synthetic providers by default. No arguments print help without creating telemetry. An explicit test mode may send labelled handshake events to a configured Guardian; examples must not call a paid model or use real prompts/provider credentials. Separate tests exercise real application helpers through localhost HTTP intake/processing in an isolated database.
