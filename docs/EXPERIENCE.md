# Product experience: query.md implementation contract

Recorded 2026-09-13 before implementation, responding to [query.md](query.md). The requested outcome is a product people can understand, connect and investigate, with visible design changes and an interactive introduction. Existing numeric capture, identity, policy and notification behavior remain the data and authority boundaries.

The founder subsequently selected **Sillage** for the product name, with the meaning of understanding what passed through by the wake it leaves. [BRAND.md](BRAND.md) records the name and compatibility boundary. Apply it to visible UI and current docs; preserve configuration, integrations and stored identities.

## Gaps and decisions

1. Entry currently asks for access before explaining the product. Add a public landing page at `/welcome`, an interactive, explicitly labelled sample workspace at `/demo`, and a redesigned sign-in surface at `/signin`. Public demo content is deterministic sample data held in the browser; it never writes observations, requests private dashboard data or claims to be a connected application. The existing authenticated Overview remains `/`. Connect-app calls to action lead to `/setup` so the existing verified login round trip restores onboarding.
2. The product needs a clear visual identity. Use warm paper surfaces, dark ink navigation, restrained teal accents, readable typography, precise tables and useful trace interactions. Add a responsive application sidebar and clear page hierarchy. Avoid invented savings claims, customer logos, pretend live status and ornamental charts without meaning.
3. Setup currently exposes technical diagnostics before giving a next action. Present the actual source and four steps: create an app key, add the supported integration, send a connection test, verify a real call and processing. Explain why the key exists, where it belongs, what gets collected and how to revoke it. Human sign-in and app ingestion have distinct credentials; Guardian needs no model-provider key. Advanced JSON, diagnostic detail, monitoring rules and notifications remain available through progressive disclosure.
4. Overview and Live have different data sources/windows. Show an independently loaded recent-call snapshot using the same API as Live, plus clearly identified worker-produced accounting. A failed aggregate request must not hide available captured calls. Distinguish direct inbox/ledger processing from Langfuse source reads. Direct monitoring nests its actual health and currently reports a top-level `healthy:false` sentinel; do not present that sentinel as a permanent broken connection.
5. Trace investigation must preserve measurements. Show known duration even for failed calls and render zero duration as a point. Unknown values remain unknown. Explain that direct capture contains technical labels and numeric call measurements; raw prompts/responses, retrieval documents and full workflow outcome tracing are outside the current contract.
6. Existing identity supports operator-managed isolated workspaces. A public page can explain getting started and sign-in, but must not pretend that an email form provisions a tenant/account. New users obtain workspace membership through their configured organization identity provider/operator. Self-service registration/provisioning requires a separate persistent account lifecycle and remains an explicit release gap.
7. Integration recipes currently ask users to find and copy three repository files. Provide authenticated downloads of the exact Python or Node helper modules at `/api/guardian/integrations/{python|node}.zip`, packaged with brief instructions. Use a fixed file allowlist, include no configuration or credentials, and include the helpers in the deployment image. These remain local source modules, not published packages. Downloading helpers does not connect an app; a real captured call is the verification step.

## Acceptance and implementation sequence

- Implement the public experience and navigation, the guided connection flow, and independent source/processed-data visibility in parallel within separate files.
- Preserve named access, owner-only key controls, one-time key display, exact Origin/CSRF, callback validation, abort/stale-request guards, immutable replay and unknown-cost semantics.
- Check landing/demo at desktop and mobile sizes, interactive run/step inspection, explicit sample labelling, no private API access from public pages and meaningful get-started/sign-in actions.
- Verify fresh onboarding and existing connected states, revoked credentials, receipt versus processing, outage/error states, and mixed source/aggregate availability.
- Build the production frontend from explicit inputs, verify real local OIDC/browser/worker behavior and refresh the running preview with the verified build. Update [PLAN.md](PLAN.md), [PROGRESS.md](PROGRESS.md), [ARCHITECTURE.md](ARCHITECTURE.md), [ONBOARDING.md](ONBOARDING.md) and [VALIDATION.md](VALIDATION.md) with actual results and remaining gaps.

No external identity account, deployment, provider call, Slack message or new repository push is required for this implementation. Existing local preview data must be retained.

## Delivered and checked

The described landing/demo, Sillage identity, access/navigation, guided Connections, helper downloads and data visibility changes are implemented. The final build passed 1,259 backend tests (two platform skips), 291 frontend tests, 151 harness tests, 67 browser scenarios and all eight actual native deployment/onboarding phases. Mobile review additionally corrected hidden member/project context and crowded call rows. The existing preview is running the new build at `http://127.0.0.1:8001/welcome`, with its database preserved. [VALIDATION.md](VALIDATION.md) records exact artifacts, timings and remaining customer/deployment limits. Self-service signup/provisioning and full RAG tracing remain open product work.
