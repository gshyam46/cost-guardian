# Isolated direct-capture deployment (R2/R4)

Contract recorded on 2026-09-12 before implementation. This slice packages the existing no-Langfuse customer path and verifies a real local browser-to-worker journey. It does not provision an identity-provider account, a managed database, a public domain, shared tenancy or a billing system. Existing Langfuse development remains available through its current commands; the first packaged deployment explicitly selects direct capture and named OIDC access.

## Topology and entrypoints

One immutable application image contains the constrained Python backend and a production frontend build. It runs as an unprivileged user. The API serves the static UI and `/api` on one origin; separate processes run ingestion and optional notification delivery. An external TLS reverse proxy forwards to the API's private/loopback port. The operator supplies one authenticated, TLS-protected transaction-capable Mongo replica set and a registered OIDC confidential client. No provider/model key is needed by Guardian.

The deployment module exposes `python -m deployment` with inert no-argument help and explicit `check`, `bootstrap`, `run api`, `run worker` and `run notifications` commands. `check` validates configuration and packaged static assets without contacting Mongo, OIDC or a model provider. `bootstrap` performs the bounded database initialization described below. Runtime entrypoints validate configuration and deployment readiness before starting a role. Native commands and Compose use the same module rather than different initialization logic.

Compose starts one successful bootstrap job before API/workers. The API port binds to host loopback, not all host interfaces. Only the API is published; the package does not publish Mongo. A notification override enables the existing worker when its destination secret is supplied. The same identity/project/source configuration and secret files must reach all running roles. Secret or membership changes require consistent recreation/restart; they do not silently rebind an existing database. Workers attempt cooperative cancellation for 45 seconds and resource cleanup for up to five seconds. Compose enforces a 60-second process deadline; a native supervisor must enforce its own deadline because Python cannot forcibly cancel a task that ignores cancellation.

## Configuration and secrets

Packaged entrypoints disable dotenv loading before importing application configuration. The image build context uses an allowlist and excludes all local `.env` files, virtual environments, caches, reports, credentials and Git history. The frontend is built from explicit source/config files with a relative/same-origin API URL, visual-edit/development hooks disabled and source maps disabled. Server secrets are never build arguments or frontend variables.

Required secret-capable fields are `MONGO_URL`, `GUARDIAN_OIDC_CLIENT_SECRET` and `GUARDIAN_OIDC_MEMBERS_JSON`. Each supports its matching `_FILE` variable; optional `GUARDIAN_SLACK_WEBHOOK_URL_FILE` supplies notifications. A direct value and a file for the same field are a configuration error. Files must be regular, readable, bounded UTF-8 files; trim only a trailing newline, reject empty/oversized/invalid input, and report fixed errors without paths or values. The Compose template mounts explicit secret files, not a whole operator directory. Membership includes at least one exact verified issuer subject with the owner role.

Production requires explicit `MONGO_URL`, database name, `GUARDIAN_CAPTURE_MODE=direct`, `GUARDIAN_AUTH_MODE=oidc`, fixed organization/project/environment/connection, public HTTPS origin, issuer/client and owner membership. Reject insecure/unauthenticated Mongo configuration in production and invalid polling intervals; the supported poll interval is 1-300 seconds. Public and UI origins follow the existing exact same-origin identity contract. `GUARDIAN_ALLOW_INSECURE_LOCAL_AUTH=true` remains an explicit loopback-only development exception, including loopback-only Mongo, and must not weaken production validation.

## Bootstrap and readiness

Bootstrap is explicit, idempotent and bounded. Validate Mongo replica/session/transaction capability before initializing state. Reuse the current identity/source binding and ledger transaction invariants, create the required identity/capture/ledger/summary/policy/notification indexes, and make a fresh deployment usable before its first login. Repeated or concurrent initialization of the same binding must be safe. Reject mismatched identity/source bindings, incompatible existing ledger data and legacy cutover requirements. Never delete state, clear history, reset a cursor or reinterpret a populated database to make initialization pass. Do not contact an OIDC provider, model provider, Langfuse or Slack during bootstrap.

`GET /api/health` retains its existing process-liveness meaning. A separate unauthenticated, noncacheable `GET /api/ready` returns a small fixed ready/not-ready result after bounded configuration, database capability and matching initialized-binding checks. It must not write state, disclose connection/project/secret details, issue tokens, fetch OIDC metadata or require application traffic. API readiness is distinct from worker freshness, source completeness, notification verification and customer activation. Requiring a worker heartbeat or a first login before exposing the login page would deadlock a fresh installation.

Runtime workers retain their durable queues, leases and replay semantics. Handle termination by cancelling the selected loop and closing its database/source resources; interruption cannot falsely acknowledge pending work. Container supervision restarts failed roles. Existing authenticated Setup monitoring remains the place to inspect worker progress and blocked work; a healthy process or ready API does not mean monitoring is active.

## Same-origin UI and proxy

`GUARDIAN_STATIC_DIR` identifies an explicit production build directory. Serve the application shell only for known client routes (`/`, `/setup`, `/live`, `/incidents`, incident detail and run detail), with noncacheable HTML. Serve bounded public build assets with suitable content types and immutable caching only for hashed static assets. Reject traversal, symlink escapes, secret/source paths and missing assets. Unknown `/api` routes and API 401/404/503 responses must remain API responses, never a successful HTML fallback. Static routing must not shadow authentication/capture APIs or loosen their authority.

The TLS reverse proxy preserves the full `/api` path, Origin, cookies, CSRF and ingestion headers. It must not cache or retry mutations, log callback query strings/credentials, or buffer request bodies into unprotected disk files. Allow the existing 256 KiB intake body limit and response deadlines up to 45 seconds. Default application proxy-header trust is disabled; if the operator enables exact trusted proxy IPs, the gateway must overwrite caller-supplied forwarding headers. Pinned Uvicorn 0.25 does not interpret trusted-proxy CIDR ranges. HTTPS cookies and callback destinations derive from fixed identity configuration, not arbitrary forwarding headers.

## Verification and release boundary

Required local proof uses the actual deployment entrypoints and lifespan, built frontend, fresh owned real Mongo database, independent worker process and an isolated signing OIDC HTTP fixture. A real browser follows discovery/authorization/token/JWKS/callback behavior; no session insertion, provider replacement, API response interception or fake session-cookie injection may stand in for login.

Verify `/setup` deep-link restoration, owner identity, key creation and actual test receipt with zero production metrics; submit one synthetic terminal error using the revealed write-only key; wait for the real worker, inspect tokens/unknown cost and the incident, resolve it, replay unchanged intake without duplication/reopening, log out and verify protected access denial. Test bootstrap replay/mismatch, standalone refusal, missing configuration, readiness during Mongo outage, static/API route boundaries and controlled worker restart/cleanup. Never retain a one-time key in screenshots, logs or reports. Fixture services and descendants must be marker-owned and closed before removing only the suite's own databases.

Container configuration/build checks, native-process startup, real local OIDC/browser behavior and deployed TLS/provider acceptance are separate evidence. The local Docker CLI is installed but its engine was stopped during initial inspection; do not claim a successful image build without running one. Native-process proof must be labelled honestly. Hosted CI, public TLS, a real customer IdP, real Slack acceptance, production recovery/load, retention/offboarding and customer activation remain release gates even after local checks pass.

First-package Mongo authentication is explicitly username/password URI authentication with valid TLS, including SRV; X.509/workload-identity configuration is outside this slice. Readiness snapshots validated configuration once per API process, so each probe performs bounded database reads without reloading the UI build.

Local verification on 2026-09-12 passed the actual native browser-to-worker journey, including two signed OIDC logins, owner key/test, synthetic production-path capture, committed resolution/replay, restart and database-outage recovery. The complete backend suite passed 1,230 tests with one Windows symlink privilege skip. Compose and the allowlisted frontend build passed their checks; the application Docker image and public TLS/IdP deployment remain unverified.
